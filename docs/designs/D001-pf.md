# PF 产品契约

- **状态：** 草案
- **范围：** Python 直接依赖下界
- **初始生态：** 使用 uv 管理的项目和 workspace
- **实现设计：** [D002](D002-pf-implementation.md)
- **搜索算法：** [D003](D003-pf-search-algorithm.md)
- **ty 增量静态检查：** [D004](D004-pf-ty-enhancement.md)

本文定义 PF v1 的用户可见契约。内部模块放在 D002，候选探测和坐标搜索细节放在 D003，`ty` 增量静态语义放在 D004。

## 1. v1 承诺

### 1.1 Floor 的含义

单个依赖的 floor 表示：

> 在报告记录的包、cell、搜索空间、来源、构件策略、工具和测试策略下，该精确版本属于最终完整通过的坐标最小向量。

一个 cell 为：

```text
(精确 uv target triple, CPython minor, extra 兼容面)
```

PF 按确定顺序反复降低直接依赖。最终向量固定其他坐标后，没有任何单个受管依赖还能继续降低并通过完整 Evaluator。

该结果是坐标最小值，不是依赖笛卡尔积的全局最小值。PF 不证明未测试的中间版本、其他依赖组合或报告范围之外的环境兼容。

### 1.2 单调性假设

v1 假设同一 cell、同一依赖、其他坐标固定时，候选按版本升序形成：

```text
FAIL* PASS*
```

若同一切片中观察到 `v_low < v_high`，但 `PASS(v_low)`、兼容性 `FAIL(v_high)`，该 dependency/cell 立即标记为 `NON_MONOTONIC`。

PF 保存反例后停止该 cell，不继续细化、不生成 `!=`，也不允许 apply。未探测版本保持 `UNKNOWN`；v1 的结果不是完整范围认证。

### 1.3 v1 支持

- 静态的 `project.dependencies` 和 `project.optional-dependencies`；
- 单包项目和 uv workspace 中可独立安装的成员；
- CPython minor、精确 uv 目标平台和 extra 兼容面矩阵；
- 受管直接 registry 依赖的下界搜索；
- 相对最高版本诊断基线的 `ty` 增量静态定界和项目完整测试；
- major、minor、patch 搜索粒度；
- 全局或逐依赖的搜索空间；
- 确定、可合并的 `package-floor.json`；
- 保守的 `pyproject.toml` apply；
- `pf check` 验证当前声明。

### 1.4 v1 不支持

- 最小化传递依赖；
- 搜索直接依赖的笛卡尔积；
- 非单调区间细化或自动生成排除项；
- 自动发现、生成或收紧不兼容上界；
- baseline 失败后的版本恢复；
- failure attribution、partial tests 或测试用例选取；
- 没有完整测试的 static-only floor；
- 跨运行持久化 Evaluation 或 Proposal 环境；
- 自动识别或重试 flaky tests；
- 执行非宿主目标平台；
- 将 workspace 视为一个兼容性域；
- 应用不完整、过期或无法表示的证据。

## 2. 搜索单位与依赖

### 2.1 包边界

搜索单位是一个可独立安装的分发包。workspace root 只有在自身也是包时才是搜索单位；每个可安装成员拥有独立搜索和报告。

省略 `packages` 时，PF 选择所有发现的可安装单位，再应用 `exclude-packages`。

workspace 提供成员发现、默认配置、uv 来源/index、root 测试依赖和本地依赖快照。它是配置上下文，不是解析域；无关同级成员不得参与。

### 2.2 依赖声明

PF 保留每条声明的稳定 ID、base/extra 位置、规范化名称、请求 extras、版本约束、marker、来源和源码位置。

同一位置中，同名声明的活跃 cell 必须两两不相交。重叠或完全重复均为配置错误。

同一名称可以同时位于 base 和 optional group；同一 cell 中的约束取交集。

`project.dependencies` 和 `project.optional-dependencies` 必须是静态元数据。任一字段为 dynamic 时，PF 保守失败。

`pf check` 接受合法 PEP 508 marker。受管 search/apply 只投影：

- `python_version`；
- `sys_platform`；
- `platform_machine`。

依赖若使用其他 marker 维度，必须设为非受管。

### 2.3 受管依赖

`managed-deps` 和 `unmanaged-deps` 决定 PF 可以移动和改写哪些直接依赖，两者互斥。

```text
存在 managed-deps    managed = 可搜索直接依赖 ∩ managed-deps
存在 unmanaged-deps  managed = 可搜索直接依赖 − unmanaged-deps
两者均不存在          managed = 所有可搜索直接依赖
```

`managed-deps = []` 表示不搜索任何依赖。root 默认列表中的未知名称被跳过；包级白名单中的未知名称属于错误。

这两个配置只影响 search/apply。`pf check` 验证所有活跃直接依赖。

### 2.4 可搜索依赖与固定依赖

没有下界或包含 `>=`/`>` 下界的直接 registry 依赖可以搜索。已有 `>=`/`>` 不限制向下探索。

已有 `<`、`<=` 和 `!=` 始终筛选候选并原样保留。Apply 将最终精确 floor 写成 `>=`，因此可以替换或规范化已有 `>=`/`>`。

`==`、`===`、`~=`、URL、VCS、path 和 workspace-source 依赖均为固定依赖。它们参与每个 Proposal，但不搜索、不改写。

默认管理范围排除固定依赖。在 `managed-deps` 中显式指定固定依赖属于错误；在 `unmanaged-deps` 中指定会产生冗余警告。

### 2.5 来源

候选发现和安装必须使用同一个有效来源。v1 支持 registry/named index、快照内 path/workspace、精确 Git commit 和带完整性信息的 URL/archive 固定依赖。

来源组合不受支持或存在歧义时保守失败。报告和日志不得存储凭据。

Index 标识不是搜索维度。构件 hash 或来源身份变化会使证据失效，并标记为 `SOURCE_CHANGED`。

## 3. 兼容矩阵

配置矩阵是以下维度的乘积：

```text
精确 uv target triple × CPython minor × extra 兼容面
```

每个进程只执行与宿主精确匹配的目标平台；其他平台由对应宿主生成报告，再通过 merge 合并。

### 3.1 Python

配置使用类似 `"3.11"` 的 minor。每次运行使用该 minor 当前最新稳定 CPython patch，并记录完整版本、implementation 和 ABI。

省略时，根据 `requires-python` 和可用稳定 CPython minor 推断。v1 不支持 PyPy、free-threaded 或 debug 解释器。

### 3.2 目标平台

目标平台使用完整 uv triple，例如：

```toml
platform = ["x86_64-unknown-linux-gnu"]
```

粗粒度 `linux`、`macos`、`windows` 无效。省略时默认为精确宿主目标平台。

### 3.3 Extra 兼容面

```text
extras = "none"  -> [ [] ]
extras = "each"  -> [ [], 每个单独 extra ]
extras = "all"   -> [ [], 每个单独 extra, 最大组合 ]
```

`extra-surfaces` 是显式形式。它必须包含 `[]` 和每个 extra 的单元素兼容面，还可以增加组合；它与 `extras` 互斥。

## 4. 候选策略

### 4.1 候选快照

CandidateBuilder 在每个 dependency/cell 首次查询 index 后，冻结规范化、有序的精确版本列表。本次 search 不再刷新。

报告记录候选摘要、代表样本、实际 probe、来源和构件 hash。运行中途发布的新版本不参与本次结果。

候选排除 yanked 版本，默认排除预发布。`distribution` 支持：

- `wheel`：必须存在匹配 cell 的 wheel；
- `sdist`：强制使用候选 sdist；
- `any`：优先 wheel，否则使用 sdist。

默认值为 `wheel`。

### 4.2 搜索粒度

`release-granularity` 支持 `major`、`minor`、`patch`，默认为 `minor`。

major/minor 粒度使用该系列在候选快照中的最新合格稳定 patch 作为代表样本。报告和 apply 始终保留实际验证的精确版本。

例如通过的是 `1.24.4`，PF 写入 `>=1.24.4`，不会把它截断为未经验证的 `>=1.24`。

系列按 PEP 440 的 epoch 和 release tuple 分组；缺失分量补零。Pre/dev 默认被过滤，post release 仍属于其基础 patch 系列。

### 4.3 搜索空间

`search-space` 与搜索粒度正交。标量形式支持：

- `all`：全部合格历史版本；
- `current-major`：只搜索 baseline 所在 major；
- `current-minor`：只搜索 baseline 所在 minor。

默认值为 `all`。

搜索空间锚定每个依赖的 baseline 精确版本。比搜索空间更粗、没有意义的粒度组合属于配置错误。

标量空间的合法组合为：

```text
all            × major | minor | patch
current-major  × minor | patch
current-minor  × patch
```

列表形式逐依赖覆盖，例如：

```toml
search-space = [
    "numpy>=1.0,<2.0",
    "pydantic>=2.1,<3",
]
```

列表使用 `packaging.Requirement` 解析，只接受名称和非空版本 specifier。Extras、marker、URL 和来源无效。

规范化后同名重复、未知直接依赖或最终候选集为空均为配置错误。未列出的受管依赖使用 `all`。

有效候选是搜索空间、已有 `<`/`<=`/`!=`、构件策略和“不高于 baseline”的交集。搜索空间只影响探测，不写入项目依赖声明。

## 5. Evaluation 契约

### 5.1 源快照与隔离

每次 search 使用当前工作树的不可变源快照。tracked、staged、unstaged 和未忽略的 untracked 源文件都在范围内。

`.git`、虚拟环境、工具缓存、`.pf`、PF 临时目录和 `package-floor.json` 不进入快照。

每个新 Proposal 获得隔离的可写副本和虚拟环境。PF 不使用 Git worktree、workspace lock、操作者 `.venv`、`uv sync` 或 `uv run`。

### 5.2 安装

PF 使用显式解释器和底层 `uv pip` 安装 editable 包及其兼容面。受管直接依赖物化为 Proposal 中的精确版本。

非受管直接依赖保留原约束；传递依赖使用 uv 正常解析。Proposal 记录完整解析图和实际安装向量。

测试依赖安装前先冻结目标依赖图。测试支撑环境可以增加工具，但不得改变目标依赖图，否则为 `HARNESS_ERROR`。

### 5.3 Static 与 Full Evaluator

每个 cell 先按最高版本策略解析当前声明，得到 `V_hi`，并在该环境运行一次 `ty`。这次规范化诊断集合冻结为 `S_hi`。

`StaticEvaluator` 执行：

```text
resolve/install -> ty -> increment vs S_hi
```

静态通过表示相对 `S_hi` 没有新的诊断身份，而不是 `ty` 退出码为 0。项目既有 typing 错误保留在 `S_hi` 中，不构成兼容性失败。

`FullEvaluator` 对精确 Proposal 先复用已有 `STATIC_PASS`；未命中时补跑带 `S_hi` 的静态检查。只有静态通过后才运行完整 `test-command`。

`pf check` 与 search 使用同一增量规则。细节见 [D004](D004-pf-ty-enhancement.md)。

v1 不选择测试子集，也不做 failure attribution。没有完整测试命令时，search/apply 属于配置错误。

`test-command` 是不经过 shell 的 argv 数组，不能以 `uv run` 开头。默认 cwd 为包目录；`command-cwd = "root"` 选择快照 root。

测试要求 `test-group`，默认 `"test"`。PF 从 workspace root 和包读取该组，展开 `include-group` 后先 root、后 package 合并。

来源冲突、约束交集为空，或测试依赖改变目标图，都属于 `HARNESS_ERROR`。

### 5.4 状态

只有以下状态可以建立搜索边界：

```text
PASS         完整兼容性判据通过
STATIC_FAIL  ty 相对 S_hi 出现增量诊断
TEST_FAIL    完整测试正常失败
```

以下状态不属于兼容性证据：

```text
UNAVAILABLE
BUILD_UNAVAILABLE
UNRESOLVABLE
HARNESS_ERROR
SOURCE_ERROR
TOOL_ERROR
TIMEOUT
```

遇到非证据状态时，PF 保存不完整报告并停止该 cell。它们不能被当作失败边界，也不能由二分搜索跳过。

`test-failure-exit-codes` 默认为 `[1]`。其他非零退出码、信号或启动失败属于工具或支撑环境错误。

### 5.5 确定性

v1 假设 `test-command` 对相同 Proposal 是确定的。同一精确 Proposal 的完整测试只执行一次并缓存。

PF 不自动重试 flaky tests。若显式重跑观察到同一 Proposal 同时 `PASS` 和 `TEST_FAIL`，结果为 `NONDETERMINISTIC`，停止该 cell 并禁止 apply。

## 6. 搜索结果

### 6.1 Baseline

每个 cell 都从当前源码快照和当前依赖声明开始，在全新环境按正常最高版本策略解析，得到 `V_hi`。这次解析同时捕获 `S_hi`。

Baseline 不读取 lock、操作者环境或既有安装。它必须通过 FullEvaluator：相对 `S_hi` 静态通过（对 `V_hi` 为恒真），并且完整测试通过。

项目既有 `ty` 诊断不产生 `BASELINE_FAILED`。完整测试失败才是 baseline 的兼容性失败。基础设施或不确定状态按对应错误停止；无法捕获 `S_hi` 时同样停止。PF 不尝试降级恢复。

### 6.2 两阶段搜索

PF 先使用 StaticEvaluator 做完整的坐标定界，得到静态通过的不动点 `V_static`。

随后对 `V_static` 运行一次 FullEvaluator。通过时直接返回；失败时从完整通过的 baseline 开始，用 FullEvaluator 做动态坐标搜索。

两阶段都覆盖全部受管依赖，按规范化名称排序，并反复扫描直到一整轮没有坐标下降。

详细算法和终止证明见 [D003](D003-pf-search-algorithm.md)。

### 6.3 Floor

单个 dependency/cell 的结果包含：

- 最终精确版本；
- 完整最终向量；
- 搜索空间和粒度；
- baseline、静态和动态 probe；
- 通过/失败边界证据；
- 来源、构件和工具身份。

v1 不搜索上界。`observed_upper = null` 表示未搜索、未观察，不表示无限兼容。

若显式搜索空间中没有任何通过样本，结果为 `NO_PASS_IN_SEARCH_SPACE`，不能用空间外 baseline 冒充 floor。

### 6.4 跨 cell 投影

Apply 前，PF 将各 cell 的精确 floor 投影回依赖声明。相同 floor 可以合并；不同 floor 必须用受支持 marker 表示。

base 和 optional declaration 保持原位置。组合 extra 才需要的约束若无法由真实 extra 表示，PF 报告结果但拒绝 apply。

缺失 cell、目标平台属性无法表示或 marker 覆盖不完整时，不得推断约束。

## 7. 命令

```text
pf check [package]
pf search [package] [--jobs auto|N] [--max-duration DURATION]
pf apply [package]
pf minimize [package] [--jobs auto|N] [--max-duration DURATION]
pf explain [package] [filters]
pf merge REPORT... --output PATH
```

### 7.1 check

`check` 验证当前声明，不搜索、不读取推荐结果。每个 cell 先按最高版本策略解析并运行 `ty`，冻结 `S_hi`；再将所有活跃直接依赖作为 top-level 输入，使用 `uv pip --resolution lowest-direct`。

固定版本、marker、排除项、上界和来源保持不变。`lowest-direct` 向量通过携带 `S_hi` 的 FullEvaluator 验证：无增量诊断且完整测试通过。最高版本环境只用于捕获 `S_hi`，不在其上运行测试，也不把最高版本测试结果当作 check 证据。

### 7.2 search 与 minimize

`search` 更新匹配 cell 的 `package-floor.json`，绝不编辑元数据。不完整报告是合法输出，但不能 apply。

`minimize` 等价于先 search 再 apply。Search 不完整或失败时，不进入 apply。

### 7.3 apply

`apply` 是纯粹的“报告到元数据”转换，不执行解析、`ty` 或测试。

它要求所有目标 cell baseline 通过、搜索到达不动点、最终向量完整通过、策略和来源未漂移、覆盖完整且结果可表示。

`NON_MONOTONIC`、`NONDETERMINISTIC`、`NO_PASS_IN_SEARCH_SPACE`、超时、非证据状态、项目漂移或缺失 cell 都会禁止 apply。

受限 `search-space` 可以 apply，但必须进入报告和策略身份。Apply 只写精确 `>=floor`，并原样保留已有上界与排除项。

### 7.4 explain 与 merge

`explain` 读取完整或不完整报告，不调用 Evaluator。

`merge` 只接受包、Schema、来源和策略身份一致的报告。Cell 以目标平台、Python minor 和规范化 extra surface 为 key。

相同 cell 的重复结果必须完全一致；冲突导致失败。Merge 不按时间戳选胜者，也不调用 Evaluator。

## 8. 报告与可靠性

### 8.1 公共报告

`package-floor.json` 是 apply、explain 和 merge 使用的带版本公共接口，不是 Evaluation 缓存。

报告包含 Schema/生成器版本、包和快照身份、候选快照、策略、cell、解释器、依赖声明、来源、构件 hash、Proposal、`S_hi`、Evaluation、floor 和投影证据。

命令输出只保留脱敏摘要和有界尾部。未知 Schema 保守失败，序列化顺序规范化，写入原子完成。

### 8.2 缓存与环境生命周期

Evaluation 和 Proposal 环境只在单次 search 内有效。

`ty` 环境保留到本次 search 结束。身份完全相同且尚未运行测试的环境，可以直接晋升为一次 FullEvaluator。

环境一旦运行测试就视为可能污染，只保留诊断，不再作为干净环境复用。不同 Proposal 不通过原地升级或降级依赖复用。

Search 结束后默认清理 Proposal 环境。跨运行只复用 uv 下载、wheel 和 build cache。

### 8.3 并行与时限

单个 cell 内的 Proposal 串行执行。相互独立的包、Python、平台和 extra cell 可以共享全局并发限制器。

`jobs` 接受 `auto` 或正整数。输出和报告顺序始终规范化。

默认阶段超时：

```text
resolve-timeout = "10m"
ty-timeout      = "10m"
test-timeout    = "30m"
```

`"none"` 显式禁用对应超时。达到 `--max-duration` 后停止调度、保存不完整报告并禁止 apply。

### 8.4 退出码

```text
0  成功
1  当前声明或 baseline 的兼容性判据失败
2  没有可应用的 floor，包括 NON_MONOTONIC/NONDETERMINISTIC/NO_PASS_IN_SEARCH_SPACE
3  用法、配置、Schema、覆盖或项目漂移错误
4  基础设施错误、超时或其他不确定结果
```

## 9. 配置

PF 读取 `[tool.pf]`。包级覆盖使用 `[tool.pf.package.<name>]`。

```toml
[tool.pf]
packages = ["carda-core", "carda-silk"]
exclude-packages = []

python = ["3.11", "3.12"]
platform = ["x86_64-unknown-linux-gnu"]
extras = "each"

release-granularity = "minor"
search-space = "all"
distribution = "wheel"
allow-prereleases = false
```
