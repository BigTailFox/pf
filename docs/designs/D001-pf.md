# PF 产品与命令契约

- **状态：** 现行
- **版本：** v1 / `package-floor.json` Schema 1
- **最后核对：** 2026-08-21
- **实现结构：** [D002](D002-pf-implementation.md)
- **搜索算法：** [D003](D003-pf-search-algorithm.md)
- **静态证据：** [D004](D004-pf-ty-enhancement.md)
- **失败与诊断：** [D005](D005-pf-failure-and-diagnose.md)
- **CLI 交互与展示：** [D006](D006-pf-cli-enhancement.md)

本文是 PF v1 产品结果、命令与参数语义、配置、报告、apply 和退出码的唯一所有者。模块接口以 D002 为准，单 cell 的 probe 与坐标搜索以 D003 为准，`ty` 诊断基线和增量语义以 D004 为准，Attempt、失败分类与 `diagnose` 语义以 D005 为准，CLI help、调用错误、结果摘要和 `explain` 展示以 D006 为准。

## 1. 结果承诺

### 1.1 搜索单位

PF 的搜索单位是一个可独立安装的分发包和一个兼容性 cell：

```text
(精确 uv target triple, CPython minor, extra 兼容面)
```

workspace 只提供成员发现、配置、来源和测试支撑上下文，不是一个共同解析域。root 只有在自身可安装时才是搜索单位；每个成员拥有独立报告。

### 1.2 Floor

在报告记录的源码快照、cell、来源、候选策略和测试策略下，PF 返回一个经过完整 Evaluator 直接验证的坐标最小向量。固定最终向量中的其他受管直接依赖后，没有任何单个坐标还能降低到冻结候选中的更早样本并通过。

它不是依赖笛卡尔积的全局最小值，也不证明未探测的中间版本、其他依赖组合或报告范围外环境兼容。

v1 假设每个一维切片为 `REJECTED* PASS*`。观察到更低版本通过而更高版本被 Rejected 时，该 cell 以 `NON_MONOTONIC` 停止并禁止 apply。完整算法见 D003，Rejection 的资格由 D005 定义。

v1 只发现下界，不搜索、生成或收紧不兼容上界。已有上界与排除项原样保留。

## 2. 项目与依赖范围

### 2.1 元数据

PF 支持静态的 `project.dependencies` 和 `project.optional-dependencies`。任一字段由 `project.dynamic` 提供时保守失败。

每条声明保留稳定 ID、base/optional 位置、规范化名称、requested extras、specifier、marker、来源、原文和 `pyproject.toml` 路径。同一位置中同名声明在任一活跃 cell 上不得重叠；base 与 optional group 中的同名约束在共同活跃时取交集。

`pf check` 可以验证任意合法 PEP 508 marker。参与 search/apply 的受管声明只允许由以下 marker 维度投影：

- `python_version`；
- `sys_platform`；
- `platform_machine`。

使用其他 marker 维度的声明必须显式设为非受管。

### 2.2 受管与固定依赖

`managed-deps` 与 `unmanaged-deps` 互斥：

```text
存在 managed-deps    managed = 可搜索直接依赖 ∩ managed-deps
存在 unmanaged-deps  managed = 可搜索直接依赖 − unmanaged-deps
两者均不存在          managed = 所有可搜索直接依赖
```

`managed-deps = []` 表示不移动任何依赖。显式把固定依赖放入 `managed-deps` 是配置错误。

没有下界或含 `>=` / `>` 下界的直接 registry 依赖可搜索；已有下界不限制向下探索。已有 `<`、`<=` 和 `!=` 始终筛选候选并在 apply 时保留。

`==`、`===`、`~=`、直接 URL、Git、path 和 workspace-source 依赖是固定依赖。它们参与 Proposal 的解析和测试，但不搜索、不改写。

`pf check` 验证所有活跃直接依赖，不受 managed/unmanaged 选择影响。

### 2.3 来源

候选发现与安装消费同一份来源计划。v1 支持：

- 唯一、明确的 registry/default 或 named index；
- 源快照内的 path/workspace 固定依赖；
- 精确 Git commit；
- HTTPS 且带单一 SHA-256 的 PEP 508 直接 URL，以及带完整性信息的 uv URL source。

可变 Git ref、无完整性信息的 URL、歧义 index 组合及越过项目 root 的路径均保守失败；PEP 508 直接 URL 还拒绝凭据和非 HTTPS scheme。来源 identity、报告、日志和终端输出不得保存凭据。

来源或构件身份变化会使旧证据失效。

## 3. 兼容矩阵

矩阵是以下维度的乘积：

```text
精确 uv target triple × CPython minor × extra 兼容面
```

每个进程只执行与宿主精确匹配的 target。非宿主 cell 保持缺失覆盖，必须在对应宿主运行后通过 `pf merge` 补齐。

### 3.1 Python 与平台

`python` 使用类似 `"3.11"` 的 CPython minor。省略时，PF 根据 `requires-python` 和 `uv python list --output-format json` 返回的可用默认稳定 CPython 推断。Proposal 记录实际 patch、implementation 和 ABI。v1 不支持 PyPy、free-threaded 或 debug 解释器。

`platform` 必须是完整 uv target triple，例如 `x86_64-unknown-linux-gnu`。省略时使用精确宿主 target；`linux`、`macos`、`windows` 等粗粒度值无效。

### 3.2 Extra 兼容面

```text
extras = "none"  -> [ [] ]
extras = "each"  -> [ [], 每个单独 extra ]
extras = "all"   -> [ [], 每个单独 extra, 全部 extras 的组合 ]
```

默认是 `each`。`extra-surfaces` 是显式形式，必须包含 `[]` 和每个 extra 的单元素面，可以增加组合；它与 `extras` 互斥。

## 4. 候选契约

### 4.1 快照与构件

每个 dependency/cell 第一次查询 index 后，PF 冻结规范化、升序、非空的精确候选快照；运行中新发布的版本不参与本次 search。

候选排除 yanked，默认排除 prerelease，并且不得高于 baseline。`distribution` 为：

- `wheel`：必须有匹配 cell 的 wheel，默认值；
- `sdist`：必须有 sdist；
- `any`：优先匹配 wheel，否则使用 sdist。

候选和报告始终保留实际构件 locator/hash 与精确版本。

### 4.2 粒度与搜索空间

`release-granularity` 支持 `major`、`minor`、`patch`，默认 `minor`。major/minor 系列选择快照中最新的合格精确 release 作为代表；apply 不截断版本。

标量 `search-space` 默认为 `all`：

```text
all            × major | minor | patch
current-major  × minor | patch
current-minor  × patch
```

列表形式按依赖给出非空 PEP 508 specifier，例如 `numpy>=1.24,<2`。条目不能含 extras、marker、URL 或来源；同名重复是配置错误。未列出的受管依赖使用 `all`，过滤后候选为空产生不可应用结果。

搜索空间只限制探测，不写入项目声明。显式空间可以不包含 baseline；若空间内没有通过样本，结果为 `NO_PASS_IN_SEARCH_SPACE`，不能用空间外 baseline 冒充 floor。

## 5. Evaluation 与隔离

### 5.1 源快照

一次 check/search 使用当前工作树的不可变快照，包含 tracked、staged、unstaged 和未忽略的 untracked 文件。以下内容排除：

- `.git`、虚拟环境和常见工具缓存；
- `.pf`、PF 临时目录；
- `package-floor.json`。

每个 Proposal 获得独立可写副本和虚拟环境。PF 不使用 Git worktree、workspace lock、操作者 `.venv`、`uv sync` 或 `uv run`。

### 5.2 安装与测试支撑

PF 通过显式解释器和底层 `uv pip` 安装 editable 包及其 extra surface。受管依赖物化为 Proposal 的精确版本；固定和非受管依赖保持声明语义，传递依赖正常解析。

完整检查需要 `[tool.pf].test-command` 和默认名为 `test` 的 dependency group；group 可以为空。root 与 package group 分别展开 `include-group` 后合并。测试依赖安装前后目标依赖图必须一致；确定的无解或图漂移是 D005 的 `HARNESS_CONFLICT`，工具或来源故障仍为 Indeterminate。

`test-command` 是不经过 shell 的 argv 数组，不能以 `uv run` 开头。默认 cwd 为包目录；`command-cwd = "root"` 改为源码快照 root。

### 5.3 证据状态

静态兼容性事实由 D004 唯一定义；Attempt 的 cause、disposition 与 Diagnosis 由 D005 唯一定义。产品结果只有：

```text
PASS           完整获得并通过当前验证契约
REJECTED       完整且确定地不满足当前验证契约
INDETERMINATE  未获得完整、可靠、可归属的兼容性结果
```

Probe Rejection 可以来自确定的 resolution/build/harness conflict、D004 静态回归或测试正常失败，并建立 `REJECTED* PASS*` 边界。Probe Indeterminate 不能建立边界，必须停止当前 cell。Baseline Rejection 与 Baseline Indeterminate 都因没有 PASS 锚点而终止；二者分别映射兼容性失败与不确定结果。

`test-failure-exit-codes` 默认 `[1]`。其他非零退出、signal、启动失败、timeout、来源故障或不完整输出不得伪装成 Rejection。

相同 Proposal 在相同 Evaluation context 中的完整测试在一次运行内最多执行一次；context identity 由 D002 定义。PF 不自动重试 flaky tests；冲突结果为 `NONDETERMINISTIC`。

### 5.4 终端摘要与运行日志

`check`、`smoke`、`search` 和 `diagnose` 的终端只展示可操作摘要，不直接转储外部工具的多行原始输出。D004 唯一定义 `ty` 诊断身份、多重集和规范单行事实；D005 唯一定义 Rejection/Indeterminate 的用户文案和调查入口；D006 唯一定义这些事实在 TTY、非 TTY、结果摘要和 `explain` 中的信息层级与布局。CLI 展示不能改变本节其他条款定义的产品结果或退出码。

每次会启动外部进程的 PF 命令在项目 root 下建立：

```text
.pf/logs/<UTC-run-id>/
```

每个进程得到独立、脱敏的有界详细日志。日志包含 argv、cwd、仅环境变量名、timeout、退出码/signal/start error、耗时、截断标记以及 `ProcessRunner` 已捕获的 stdout/stderr head/tail；每个元数据字段和输出片段都有独立硬上限，不承诺保存超过捕获或日志上限的原始内容。日志不得保存环境变量值或已知凭据，不进入 Proposal/report identity，也不写入 `package-floor.json`。

公共报告保存可移植 FailureRecord，但不保存 `run_id` 或本地日志路径。`.pf/logs/diagnosis-index.json` 以 `(report_generation_id, failure_id)` 关联相对进程日志；本地映射缺失不改变报告证据。

有对应日志时，终端摘要追加项目相对路径。支持 Rich hyperlink 的终端把该文本渲染为指向本地文件的 OSC 8 链接；非 TTY 和不支持链接的终端输出同一个普通路径。PF v1 不自动删除运行日志。

## 6. 命令

```text
pf check [package] [--jobs auto|N]
pf smoke [package] [--jobs auto|N]
pf search [package] [--jobs auto|N] [--max-duration DURATION]
pf apply [package]
pf minimize [package] [--jobs auto|N] [--max-duration DURATION]
pf explain [package]
pf diagnose [package] [--failure FAILURE_ID]
pf merge REPORT... --output PATH
```

`package` 可以是规范化包名、包目录或 `pyproject.toml` 路径。省略时选择 root 配置允许的全部可安装包。`--jobs` 默认为 `auto`；`--max-duration` 接受正整数加 `s` / `m` / `h`，`none` 表示不设总时限。

### 6.1 check

`check` 不搜索、不读取报告。每个宿主 cell：

1. 在 `highest` 环境捕获 D004 的静态基线，不运行测试；
2. 关闭该环境；
3. 用 `lowest-direct` 解析当前声明；
4. 用同一静态基线执行增量静态检查和完整测试。

cell 可按 `--jobs` 并发，结果顺序规范化。

### 6.2 smoke

`smoke` 不搜索、不读取或写入 floor 报告。每个宿主 cell：

1. 从当前源码快照和声明建立一次 `highest` fresh resolution；其实际安装语义是 PF 的 `uv pip install --resolution highest --editable ...`，不是 `uv.lock`、操作者 `.venv` 或 `uv sync`；
2. 运行一次 D004 `StaticEvaluator.capture`；合法 `TyCheck` 中的任意诊断只产生 warning；
3. 在同一个、尚未被测试污染的最高版本环境中复用 capture 的 static pass，运行一次完整 `test-command`；不得再次运行 `ty`；
4. 关闭环境，不发现候选、不写 `package-floor.json`、不编辑项目元数据。

所有 cell 测试通过时 `smoke` 成功，即使 `ty` 报告诊断。任一 Baseline Rejection 使 `smoke` 以兼容性失败结束；Baseline Indeterminate 使其成为不确定结果。具体分类由 D005 定义。cell 可按 `--jobs` 并发，结果顺序规范化。

`smoke` 回答“当前声明约束内尽可能新的 fresh install 是否可用”；它不能代替 `check` 对当前声明下界的验证，也不能代替 `search` 的候选探索。

### 6.3 search 与 minimize

`search` 在每个宿主 cell 上完整验证最高版本 baseline。只有 baseline `PASS` 才冻结候选并执行 D003；Baseline Rejection/Indeterminate 都终止该 cell。它更新包目录下的 `package-floor.json`，绝不编辑项目元数据。不完整报告是合法输出，但不能 apply。

同一报告世代的已有非宿主 cell 会保留；本次匹配的 cell 由新证据替换。源码、策略或声明身份变化时开始新的报告世代，不把不兼容报告强行 merge。

`minimize` 先调用与 `search` 相同的工作流；只有全部报告完整且 search 退出成功时才进入与 `apply` 相同的工作流。

### 6.4 apply

`apply` 是报告到 `pyproject.toml` 的转换，不解析环境、不运行 `ty` 或测试。它要求：

- Schema、包、源码快照、当前 Evaluation 策略和报告身份有效；
- 所有目标 cell 成功且覆盖精确完整；
- 所有投影可由受支持 marker 表示；
- 报告没有 Baseline Rejection、Indeterminate、非单调、无空间内 PASS 或其他 cell 终态。

投影先从最终证据建立精确的 `Cell -> ExactFloor`，再按 floor 分组生成 PEP 508 requirement。对每组生成的 marker，PF 必须在报告的全部 target cell 上重新求值，并同时考虑声明的 base/optional 位置；求得的 `Cell -> ExactFloor` 必须与原映射完全相等。任何漏选、多选或一个 cell 命中不同 floor 都使投影不可表示并禁止 apply。

该规则不是“marker 看起来能覆盖这些 cell”的启发式。例如 GNU 与 musl target 具有相同的 `sys_platform` / `platform_machine` marker 值；若两者 floor 不同，v1 支持的 marker 无法区分它们，投影必须失败。Extra 通过声明所在 optional group 和 cell activation 表达，不生成 `extra == ...` floor marker。

写回值是实际验证的精确 `>=version`；已有上界、排除项、marker、来源、位置、注释与无关字段保持不变。编辑使用恢复日志和原子替换，重复 apply 幂等。

### 6.5 explain、diagnose 与 merge

`explain` 只读取选中包的现有报告并展示证据，不创建环境、不评估 Proposal。

`diagnose` 只读取选中包的现有报告和可选本地 diagnosis locator。省略 `--failure` 时按规范顺序列出全部 Rejection/Indeterminate；指定后展示对应 FailureRecord。Attempt 建立前的 candidate discovery/scheduling failure 显示 cell scope，不虚构 requested vector 或 Proposal。它不访问网络、不创建环境、不启动工具、不自动重试，也不修改报告或项目。成功展示诊断返回 `0`，不继承被诊断运行的退出码。

`merge` 至少需要一个输入，并要求 generator、包、源码快照、策略、声明和目标 cell 身份兼容。相同 cell 的重复结果必须完全一致；冲突失败，不按时间戳选胜者。合并后重新计算覆盖与投影授权并原子写入 `--output`。

## 7. 报告

`package-floor.json` 是 apply、explain 和 merge 使用的公共接口，不是跨运行 Evaluation 缓存。

Schema 1 包含 generator、包和源码身份、策略 identity、声明、目标 cell、Attempt、候选快照、静态基线、ProbePass/ProbeRejection/ProbeIndeterminate、AttemptFailureScope/CellFailureScope、FailureRecord、BaselineRejection/BaselineIndeterminate、最终 Evaluation、投影证据以及 `complete | incomplete` 结果。它不保存 `run_id` 或本地日志路径。

JSON 使用排序 key、固定 separators、UTF-8 和单个末尾换行。未知 Schema、超过读取上限、非法 JSON 或结构不一致均保守失败；写入使用临时文件、`fsync` 和原子 replace。

## 8. 配置

PF 读取 root `[tool.pf]`、root `[tool.pf.package.<name>]` 和成员包 `[tool.pf]`。优先级从低到高为 root、root package override、成员包；列表替换而不是拼接。root-only 的 `packages` / `exclude-packages` 控制发现，package override 的 `path` 指定成员路径。

现行 evaluator 配置的省略默认值：

```toml
[tool.pf]
extras = "each"
release-granularity = "minor"
search-space = "all"
distribution = "wheel"
allow-prereleases = false
ty-args = []
test-group = "test"
test-failure-exit-codes = [1]
command-cwd = "package"
resolve-timeout = "10m"
ty-timeout = "10m"
test-timeout = "30m"
```

`python` 省略时从 `requires-python` 和可用稳定 CPython 推断。`platform` 省略时使用精确宿主 target。`test-command` 没有默认值，完整检查必须配置。`managed-deps` / `unmanaged-deps` 省略时全部可搜索直接依赖受管。

每个阶段 timeout 可设为 `"none"`。CLI 的 `--jobs` 与 `--max-duration` 是调度输入；它们不改变兼容性含义。`jobs`、日志表现和总时限不进入证据策略 identity。

## 9. 退出码

```text
0  成功
1  当前声明、smoke test 或 Baseline Rejection
2  没有可应用的 floor
3  用法、配置、Schema、覆盖或项目漂移错误
4  Baseline/Probe Indeterminate、基础设施错误或 timeout
```

当一个 search 同时出现多类终态时，优先级为 Baseline Rejection（1）、Indeterminate/基础设施（4）、其他不可应用结果（2）。`diagnose` 成功读取并展示记录时始终返回 `0`。

## 10. v1 非目标

- 传递依赖最小化或直接依赖笛卡尔积搜索；
- 非单调区间细化、version hole 认证或自动 `!=`；
- 不兼容上界发现；
- failure attribution、partial tests 或测试用例选择；
- 没有完整测试的 static-only floor；
- flaky 自动重试；
- `diagnose` 隐式重放或自动修复；
- 跨运行 Proposal/Evaluation 环境缓存；
- 非宿主平台执行；
- 无法表示或不完整证据的部分 apply。
